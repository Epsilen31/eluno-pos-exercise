# Step-by-step implementation walkthrough

Use this order to understand and explain the solution. Do not memorize code you cannot defend in the review.

All Java paths below are relative to `billing-service/src/main/java/com/eluno/pos/`. Open `billing-service` as the Maven project; its `pom.xml`, `src`, `.mvn`, wrappers and generated `target` are all together. Run the outer `run.py`/demo from the assignment root. Run Maven commands from `billing-service`.

1. **Frame the problem.** Read `STAKEHOLDER_REPLY.md`. Identify why blanket offer stacking, clinical rounding, ten-second billing and offline behavior need decisions. Read the original brief and state the deferred scope honestly.
2. **Start the systems.** `python run.py` builds Spring Boot and starts the unchanged Python mock. Java handles the product; Python only launches the local environment. Call `/api/health`, `/api/stores`, `/api/catalog`, and `/api/stores/HSR/staff`.
3. **Understand the packages.** Start with `controller/CheckoutController.java`, then `service/QuoteService.java`. Requests are under `dto/request`, responses and internal typed data under `dto`. DTOs are normal Lombok classes: `@Data` supplies getters/setters/equality, `@Builder` supplies a builder, and constructor annotations support construction and Jackson binding. For example, `CartLineDto.builder().variant(frame).pairRef("pair-1").build()` creates a cart line, and `line.getVariant()` reads its variant. DTOs contain normalized data, not Shopify JSON or database annotations.
4. **Trace lookup and clinical validation.** `QuoteService.findLatestValidPrescription` filters validity/customer ownership. `validator/PrescriptionValidator` checks both eyes with normal `if` statements and throws `BillingValidationException` with actionable messages. Try the demo's missing-ADD example; never modify a prescription to make a lens fit.
5. **Trace offers.** `repository/JsonRuleRepository` loads and validates JSON rules. `service/OfferService` filters conditions, builds valid offer combinations without bit masks, applies discounts in deterministic order, and records reasons. Explain a case where all stackable rules beat a single festive offer, and a case where an exclusive offer wins.
6. **Explain money.** `util/MoneyUtils` converts decimal strings and allocates discount remainders using integer paise. `service/TaxService` extracts included tax after discount and handles odd-paisa splits. Read the exact sample-invoice test. Explain why independently rounding CGST and SGST can break reconciliation.
7. **Follow checkout states and JPA.** `entity/BillingOperation`, `InvoiceSeries` and `AuditEvent` map to database tables through Hibernate. Their repositories extend `JpaRepository`. `service/CheckoutService` uses `service/OperationPersistenceService` to reserve a number transactionally, validates the accepted quote, saves PAYMENT_PENDING, calls the terminal, saves PAID, saves ORDER_PENDING, creates Shopify order and saves COMPLETED. Existing invoice-series rows are locked with `@Lock(PESSIMISTIC_WRITE)`. Network calls remain outside database transactions. An intent survives a crash, but an intent alone does not prove that a remote write failed.
8. **Review the client boundary.** `client/impl/ShopifyClientImpl` implements `ShopifyClient`, converts paise to decimal strings, attaches taxes/discount allocations, Rx properties, store/staff/channel/reference, and records the captured transaction. `client/ExternalApiClient` distinguishes known retryable mock rejections from unknown write outcomes. Request bodies have Content-Length because the supplied mock cannot read chunked bodies.
9. **Demonstrate idempotency.** Repeat a checkout reference with the same body, then with a changed total. The first returns the same saved operation; the second fails. Read integration tests simulating a committed order whose response was lost. The app recovers by reference, not by issuing another create. Unknown payment writes stop until terminal evidence is verified.
10. **Trace refunds.** `service/RefundService.calculateFullRefund` validates the original invoice and sums its exact amounts. `CheckoutService` refunds the terminal once, then writes a Shopify refund with parent sale, credit note, frame return at the billing store and no lens restock. A second full-refund reference is rejected even while the first is pending.
11. **Explain reports.** `service/DayEndReportService` counts sales on IST billing date and refunds on IST refund date, including prior-day orders. It reports gross/discounts/taxable/tax/sales/refunds/net separately and flags mismatches. Local pending payments are not invented as Shopify sales.
12. **Run and review tests.** `mvn test` starts a separate flaky mock, exercises the API, and tests rounding/discount/refund rules. `python scripts/demo.py` saves an invoice and report for your Loom. Read the known gaps before describing this as production-ready.

Before submission, change the stakeholder reply to your own voice, run the demo yourself, inspect Shopify payloads in the adapter, and explain one alternative you deliberately rejected. The provided code is a starting submission you must understand and own.

Formatting: inside `billing-service`, run `mvn spotless:apply`, then `mvn spotless:check`. The formatter uses four-space indentation. API URLs and JSON field names remain the same. Refresh/reimport the Maven project if old tabs remain open. Edit `src/main/resources/application.properties` and `schema.sql`; their `target/classes` copies are generated and overwritten by builds.
